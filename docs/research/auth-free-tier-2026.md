# Authentication choice for MyDriveLog (25 September 2026)

## Recommendation

Use **Better Auth, self-hosted in the existing Next.js app**, with its Email OTP plugin, Google provider, and the existing Neon PostgreSQL database. The framework itself is free and open source; its optional managed infrastructure has separate plans. The documented Email OTP and Google features are part of the framework, not a paid managed-infrastructure entitlement. [Better Auth pricing](https://better-auth.com/pricing), [Email OTP](https://better-auth.com/docs/plugins/email-otp), [Google provider](https://better-auth.com/docs/authentication/google).

This is the best fit for the requested flow: email address → six-digit code → full name on first use → instructor workspace, with returning users and Google users reaching the same workspace. Better Auth's OTP defaults are six digits, five-minute expiry and three verification attempts. It supports Next.js 16 and PostgreSQL directly, so the app can keep its current Vercel + Neon architecture and use the existing transactional-email service through `sendVerificationOTP`. Google OAuth requires Google client credentials and authorised callback URLs. When a Google identity's verified email matches an existing user, Better Auth links that identity by default; test that repeat Google/email sign-in resolves to one instructor workspace. [OTP configuration](https://better-auth.com/docs/plugins/email-otp), [Next.js integration](https://better-auth.com/docs/integrations/next), [PostgreSQL adapter](https://better-auth.com/docs/adapters/postgresql), [Google setup](https://better-auth.com/docs/authentication/google), [account linking](https://better-auth.com/docs/concepts/users-accounts).

“Free auth” does not mean zero operating cost: database usage, email delivery and engineering/maintenance remain ours. The current app has a home-grown magic-link challenge/session system and `instructorIdentities`, so implementation replaces that system and wires new auth users to the application's instructor/workspace model. **There are no existing instructors to migrate**, so no production identity migration is required; still test repeat sign-in and Google/email account linking to prevent duplicate workspaces. Existing code: `src/presentation/http/auth-routes.ts` and `src/infrastructure/auth/postgres-auth-repository.ts` (inspected locally).

## What “branding” does and does not mean

The app's **own email/code/name pages** can match MyDriveLog's design regardless of auth provider. That is different from the **Google-hosted consent/account-selection screen** and from **provider-generated emails or redirect domains**.

- Firebase Auth's native JavaScript SDK handles Google popup/redirect sign-in, but its passwordless email API sends a clickable link. Firebase does **not** document a native six-digit email sign-in-code entry flow equivalent to its email-link API. The link contains an out-of-band code internally, but the documented flow expects the user to click the whole link, not type six digits. [Firebase email-link flow](https://firebase.google.com/docs/auth/web/email-link-auth), [Google sign-in](https://firebase.google.com/docs/auth/web/google-signin). Firebase lets developers [edit auth email templates and use a custom-domain From address/action links](https://firebase.google.com/docs/auth/email-custom-domain), but that does not change its email-link method into typed OTP. On Spark, the [five sign-in emails/day](https://firebase.google.com/docs/auth/limits) limit remains the decisive issue.
- Google's consent screen is configured in **Google Auth Platform**, not by Firebase's login UI. Google documents app name, logo, support email, authorised domains, homepage and privacy-policy URL as branding fields. Standard sign-in only needs `openid`, `email` and `profile`; no sensitive scopes are needed for this product's basic sign-in. A published external app displaying MyDriveLog's name/logo requires [Google brand verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification), including verified domain ownership and a publicly accessible homepage/privacy policy. Google's guide says automated verification can be quick and manual review commonly takes 2–3 business days. Google's documentation states no paid-plan requirement for configuring or verifying app branding; this is an account/domain/verification process independent of Firebase billing. [Google Identity setup](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid), [brand verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification).
- Supabase lets a hosted project [edit auth email templates](https://supabase.com/docs/guides/auth/auth-email-templates) and use [custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp), including providers such as Resend and Brevo. That does **not** require Supabase Pro merely to brand the app's own login page or the OTP email. What **is** a paid add-on on a paid plan is a [custom Supabase Auth/API domain](https://supabase.com/docs/guides/platform/custom-domains), relevant if avoiding a `project-ref.supabase.co` domain in OAuth redirects/URLs matters. Its default SMTP is only for team-authorised recipients, at 2 messages/hour, so a production pilot needs custom SMTP even on a free project. [SMTP limitations](https://supabase.com/docs/guides/auth/auth-smtp).
- Better Auth's self-hosted framework leaves the first-party login page, branded email contents/sender and auth endpoint on the MyDriveLog domain under the app's control; its [Google OAuth setup](https://better-auth.com/docs/authentication/google) still requires Google's independently configured branding and callback. The framework is [free/open source](https://better-auth.com/pricing); email delivery remains a separate service cost/quota.

## Security/implementation notes for Better Auth

- Configure `storeOTP: "hashed"`; its documented default is **plain text**, even though code expiry and attempt limits are built in. Keep the short expiry and bounded attempts. [Email OTP options](https://better-auth.com/docs/plugins/email-otp).
- Keep rate limiting enabled and use `storage: "database"` (or shared secondary storage) on Vercel. Better Auth says its default in-memory counters are unsuitable for many serverless deployments; database storage requires a migration. Apply stricter endpoint-specific limits for sending and checking codes, and return a neutral response to avoid account enumeration. [Rate-limit documentation](https://better-auth.com/docs/concepts/rate-limit). The final two measures are implementation recommendations, not automatic guarantees.
- Use the existing branded transactional sender through `sendVerificationOTP`; monitor its own sending quota. For orientation, [Resend Free currently lists 3,000 emails/month and 100/day](https://resend.com/pricing?product=marketing), while [Brevo Free lists 300/day](https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans). Confirm which account/plan the app actually uses before relying on a quota.
- Disable password and magic-link UI/routes as part of migration. After verified signup, collect full name only, create/link the instructor workspace once, and redirect to Overview. A Google account with a verified matching email should reach that same instructor record; test this explicitly. [Better Auth account linking](https://better-auth.com/docs/concepts/users-accounts).

If the priority changes from owning auth data in Neon to **minimum engineering time**, Clerk is the strongest alternative on its current free tier. It is not the best architectural fit for this existing app.
